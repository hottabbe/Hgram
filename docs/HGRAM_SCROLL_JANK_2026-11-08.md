# Плавность скролла списка чатов — 8 ноября 2026

## Задача

Рывки при прокрутке списка чатов и микрофризы при смене вкладок/активити. Требовалось
добиться плавности, сопоставимой с iOS.

## Условия измерения

- Эмулятор Android API 37 x86_64 с ARM-трансляцией, 1080x2400, 12 CPU, 4 ГБ RAM.
- **Экран эмулятора — только 60 Гц** (`supportedModes` содержит один режим 60.000004 Гц).
  Поведение на 120-Гц устройствах измерением не подтверждено.
- Сборка `Hgram-v13.0.2(1260)-arm64-v8a-debug.apk`, установка `adb install -r -t`
  с сохранением аккаунта и данных.
- Метрики: `dumpsys gfxinfo` (framestats), `atrace view gfx wm`, CPU по tid из `/proc/<pid>/task`.
- Метрика `Janky frames` на эмуляторе нестабильна (Android 15 считает задержку ввода
  от синтетического `input swipe`); основные выводы сделаны по CPU потоков и счётчикам
  перерисовки, а не по этой метрике.

## Причина

Blur-снимок экрана под верхней панелью и таб-баром перезаписывался **на каждом кадре**:

1. `DialogsActivity.captureCalculateHash` включал в хеш
   `listView.computeVerticalScrollOffset()` — величину, меняющуюся на каждый прокрученный
   пиксель. Ранний выход в `DownscaleScrollableNoiseSuppressor.invalidateResultRenderNodes`
   по совпадению хеша поэтому никогда не срабатывал.
2. В результате `capture()` обходил весь видимый список и **повторно рисовал каждую
   `DialogCell`** (`RecyclerListView.captureChildren` → `drawChild`), то есть содержимое
   списка рисовалось дважды за кадр.
3. Дополнительно `RecyclerListView.captureCalculateHash` возвращает `unsupported()`, если
   активен edge-effect, — то есть при сильном скролле перезапись происходила безусловно.

Дополнительно `AndroidUtilities.setPreferredMaxRefreshRate` вызывал `updateViewLayout()`
при каждом `onResume` (вызов безусловный в `LaunchActivity`), что перекладывало весь
decor view в момент смены вкладок/активити.

## Изменения

| Файл | Изменение |
|---|---|
| `TMessagesProj/src/main/java/org/telegram/ui/DialogsActivity.java` | Хеш прокрутки квантован до высоты строки списка (`dp(56)`) — снимок перезаписывается только когда содержимое под blur действительно изменилось. |
| `TMessagesProj/src/main/java/org/telegram/ui/DialogsActivity.java` | Пока идёт скролл списка, blur-снимок замораживается (`blur3_IsScrolling()`), после остановки обновляется один раз. |
| `TMessagesProj/src/main/java/org/telegram/messenger/AndroidUtilities.java` | `updateViewLayout()` вызывается только при реальном изменении частоты обновления. |

## Измерения

Обе версии собраны из одного кода (контрольная — с откаченными правками), одинаковый
список чатов, одинаковый сценарий: 14 свайпов вверх-вниз.

### Нагрузка на потоки за флинг

| Поток | Контроль | С исправлением |
|---|---|---|
| RenderThread | **7230 + 920 = 8150 мс** | **830–1030 мс** |
| UI-поток (`org.hgram`) | 670–730 мс | 560–990 мс |
| Пул битмапов (`pool-13`) | 260–500 мс | 0–580 мс |

RenderThread просел примерно в 8–10 раз.

### Счётчик перерисовки blur-снимка

Временно добавлены счётчики в `DownscaleScrollableNoiseSuppressor`
(инструментация после проверки удалена):

| Вариант | Вызовов `invalidateResultRenderNodes` | Фактических capture |
|---|---|---|
| Без заморозки | 234 | **291** |
| С заморозкой | 55 | **37** |

Во время скролла счётчики не растут (`scrollState=1/2`), после остановки (`scrollState=0`)
снимок обновляется один раз.

### Смена вкладок (нижний таб-бар)

| Вариант | Janky frames | p99 |
|---|---|---|
| Контроль | 50 / 44 / 47 | 40 / 32 / 32 мс |
| С исправлением | 45 / 44 / 51 | 38 / 34 / 42 мс |

Разница в пределах шума измерений. Рост относительно первоначального замера (14 janky)
объясняется изменившимся содержимым списка чатов между прогонами, а не правками:
контрольный APK на том же контенте даёт те же 10–12 %.

## Проверки

- Визуально: после прокрутки вниз и обратно blur под таб-баром соответствует текущей
  позиции списка, «залипания» старого снимка нет.
- `./gradlew :TMessagesProj:compileDebugJavaWithJavac` — BUILD SUCCESSFUL.
- `./gradlew :TMessagesProj:assembleDebug` — BUILD SUCCESSFUL.
- `./gradlew :TMessagesProj:testDebugUnitTest` — 81 тест, 0 ошибок, 0 пропусков.

## Ограничения

- Экран эмулятора 60 Гц: выигрыш от `Choreographer60FpsContent.setTargetFps` (привязка
  к реальной частоте дисплея) на нём не проявляется и на 120-Гц устройствах не измерен.
- `RefreshRateController` в проекте остаётся неиспользуемым (закомментирован в
  `LaunchActivity`), поэтому понижение до 60 Гц при низком FPS не работает.
- Микрофон, реальные звонки и нативные модули этим заходом не проверялись.

# Заход 2 — микрофризы при смене вкладок (7–8 ноября 2026, вечер)

## Задача

Устранить микрофризы при смене нижних вкладок (Chats/Contacts/Settings/Profile) и при
свайпе между ними. Основная жалоба — «рывки скролла списка чатов, особенно при быстром
и сильном скролле» и «микрофризы при смене вкладок/активити».

## Диагноз: узкое место — не UI-поток, а GPU

Замеры на эмуляторе (framestats) при смене вкладок:

| Метрика | Значение |
|---|---|
| UI-поток (`HandleInputStart` → `PerformTraversalsStart`) | p50 **0.57 мс**, p95 2.9 мс |
| RenderThread (`IssueDrawCommands` → `SwapBuffers`) | p50 3.1 мс, p95 5.2 мс |
| `eglSwapBuffersWithDamageKHR` (GPU) | **9.9–10.7 мс** при смене вкладок против **2.5 мс** в покое |
| `FillRectOp` за кадр | **58** при смене вкладок против **7** в покое |
| Итоговый кадр | 19.5 мс при бюджете 16.7 мс |

UI-поток тратит меньше миллисекунды — сокращать работу в нём бессмысленно.
Вся стоимость в растеризации: приложение рисует **полноэкранный** слой 1080×2400
для blur под нижней панелью табов.

## Причина

`MainTabsActivity.iBlur3SourceTabGlass` — источник размытия под таб-баром:

1. `renderNodeCalculateHash` (`MainTabsActivity.java:198-199`) добавлял в хеш
   `fragmentPosition.left/top` фрагментов. При свайпе `left` меняется каждый кадр →
   хеш всегда новый → `RenderNodeWithHash.updateDisplayListIfNeeded` перезаписывал
   полноэкранный RenderNode 1080×2400 **на каждом кадре анимации**.
2. `renderNodeUpdateDisplayList` (`MainTabsActivity.java:207-235`) при каждой перезаписи
   рисует `canvas.drawColor` + `translate(fragmentPosition)` + `source.draw(...)` —
   то есть ещё раз отрисовывает размытое содержимое активной страницы поверх всего экрана.
3. `onViewPagerTabAnimationUpdate` (`MainTabsActivity.java:875-889`) вызывал
   `blur3_invalidateBlur()` и `contentView.invalidate()` каждый кадр. `contentView` —
   корень `fragmentView` (`ViewPagerActivity.java:124`), содержащий viewPager с обеими
   страницами, `fadeView` и `tabsViewWrapper`, то есть инвалидировалось всё дерево.

## A/B-атрибуция (runtime-флаги, одна сборка)

Чтобы отделить вклад каждой причины, в сборку были временно внесены переключатели
(после проверки удалены):

| Вариант | `eglSwap` | `FillRectOp`/кадр | GPU-проходы |
|---|---|---|---|
| Базовая (все три причины) | **9.86 мс** | 43.8 | полный экран 1080×2400 |
| Без `contentView.invalidate()` | 9.24 мс | 43.6 | полный экран |
| Без стекла табов вовсе | 8.03 мс | 49.8 | полный экран |
| С замороженным пересчётом хеша | **6.57 мс** | 58.3 | **полоса 1080×63** |

Ключевое наблюдение: при замороженном пересчёте хеша RenderThread рисует **полосу
1080×63** вместо 1080×2400 — вся стоимость была в полноэкранной перезаписи.
`contentView.invalidate()` вклад в стоимость почти не даёт (страницы и так
инвалидируются через `setTranslationX`), но заставляет перерисовывать всё дерево.

## Изменения

| Файл | Изменение |
|---|---|
| `MainTabsActivity.java` | Хеш blur-источника табов считается по квантованной позиции фрагмента (`blur3PositionQuantum = 16` px) вместо точной — перезапись полноэкранного слоя происходит на порядок реже. |
| `MainTabsActivity.java` | На время анимации табов перезапись снимка замораживается (`blur3_isTabAnimating`), снимок обновляется один раз в `onViewPagerScrollEnd`. |
| `MainTabsActivity.java` | Убран `contentView.invalidate()` из `onViewPagerTabAnimationUpdate` — страницы позиционируются собственным `setTranslationX`. |
| `HgramVoiceProcessor.kt` | `process()` теперь всегда возвращает позицию буфера в 0 (раньше при `VOICE_OFF`/`VOICE_FOCUS` позиция оставалась на месте, и вызывающий код читал смещённые данные). |
| `HgramVoicePipelineTest.java` | Тест получил Robolectric-раннер и `@Before`, инициализирующий `ApplicationLoader.applicationContext` — до этого он падал с NPE и **никогда не проверял** заявленное поведение. |

## Измерения A/B (одинаковый сценарий, одна и та же машина)

Флинг списка чатов, 14 свайпов вверх-вниз, CPU-время потоков:

| Поток | Контроль (`/tmp/apk_baseline.apk`) | С исправлением |
|---|---|---|
| RenderThread | 620 / 760 / 860 / 990 мс | **560 / 710 / 750 / 770 мс** |
| UI-поток | 560 / 560 / 730 / 910 мс | 430 / 460 / 560 / 560 мс |

Пропущенные vsync за флинг: контроль — 0…25 из 88–117, с исправлением — **0…2 из 51–118**.

Смена вкладок, `eglSwap` (GPU, atrace `view gfx`):

| Вариант | eglSwap |
|---|---|
| Контроль | 6.91 / 9.51 / 6.60 мс |
| С исправлением | **4.89 / 5.49 / 5.52 мс** |

`Janky frames` при смене вкладок остаётся в шуме эмулятора (контроль 0–6.2 %,
исправление 1.4–10.7 %) — метрика на программном растеризаторе нестабильна,
поэтому выводы сделаны по объёму GPU-работы и CPU потоков.

## Проверки

- `./gradlew :TMessagesProj:compileDebugJavaWithJavac` — BUILD SUCCESSFUL.
- `./gradlew :TMessagesProj:assembleDebug` — BUILD SUCCESSFUL.
- `./gradlew :TMessagesProj:testDebugUnitTest` — **82 теста, 0 падений** (было 82/1:

- APK `Hgram-v13.0.2(1260)-arm64-v8a-debug.apk` установлен через `adb install -r -t`,
  **аккаунт и данные сохранены** (проверено скриншотом списка чатов).
- Визуально: размытие под таб-баром не «залипает» после скролла, свайп между
  вкладками корректен, блюр под панелью соответствует активной странице.
- Инструментация (runtime-флаги `HgramPerfDebug`) после замеров удалена — в дереве
  её нет, рабочее дерево содержит только содержательные правки.

## Ограничения

- Экран эмулятора **только 60 Гц**; выигрыш от привязки к refresh rate не проявляется,
  120-Гц устройства не измерялись.
- GPU-растеризатор программный (`skiagl`), абсолютные тайминги GPU завышены
  относительно реального устройства; сравнения A/B внутри одной машины валидны.
- Настоящие 120-Гц устройства и реальные голосовые записи не проверялись.
